Three systems. The same recorded journey.

SLAM is how a robot estimates where it is while building a map. Here we replay the same saved robot journey to DVM, COVINS and Custom SLAM, then measure the estimates they produce. Only one system runs at a time.

What will happen next, and how long does it take?

For each condition: save/check one shared input → run one system → evaluate it → repeat with fresh processes. Ten inputs × three systems × three repetitions = 90 trials. Replay alone requires 11 hours 15 minutes; input capture, checks and shutdown add time. A final independent audit comes afterward. The laptop publishes checkpoints about every five minutes; this is not a second-by-second stream.

Why replay saved input instead of running each system separately in Webots for hours?

For this fixed-route estimation comparison, replay gives tighter control over the input. We want to compare what each deployment estimates from a shared journey. Separate live sessions can differ in observations or timing unless those differences are controlled and checked. Saving the input once makes its identity explicit and lets every repeat reuse the same observations on its assigned sensor channels.

Benefit for this questionWhat it means here
Matched exposureA route or sensor realization does not quietly change between entries. Sensor allocation still differs: equal recordings do not make this an equal-sensor comparison.
Inspectable failuresThe input that preceded a failure is preserved for review. Repeats can test process variability on that input; identical outputs are not guaranteed.
Separate capture from estimationWe avoid regenerating the same simulated scene for each trial. Host load, disk delivery and middleware still affect timing. No speedup or energy saving has been measured against separate live runs.

Duration and test design answer different questions. This study still runs each algorithm at recorded 1× timing, including a 30-minute endurance condition. Many short fresh-process repeats do not establish hours of uninterrupted operation; longer recordings or continuous live sessions are needed for that endurance question.

Use long live Webots runs for closed-loop missions and integration. When SLAM changes navigation, its estimates affect the route and future observations. Recorded replay cannot reproduce that feedback. Live tests are needed for navigation, collision responses and simulator/sensor/control interaction under the tested conditions; physical-robot claims need physical tests.

Carefully controlled separate live runs are also valid. Our preference is a methodological judgement for this scoped comparison, not measured proof that replay is universally superior. It does not establish map completeness, broad robustness or independence of repeated views.

Methodological basis: SLAMBench2: dataset-based comparison with specified metrics; official ROS recording/replay tutorial. These support the general method; they do not validate our deployments. This study uses its own recorded-input adapters, not a claim that it runs SLAMBench2 or rosbag.

NEW TO SLAM? / START HERE
How to read this dashboard


SLAM means Simultaneous Localization and Mapping: estimating where the robot is while building a representation of its surroundings. This study asks how three configured systems estimate the same recorded motion. Its main focus is mapping, localization, robustness and resource use.


A useful reading order
  1. Check the phase. Recording means Webots is collecting input; replay means one SLAM configuration is processing it. A fresh heartbeat means the runner is reporting, not that SLAM is working.
  2. Understand the shared input. The same recorded route is reused for the three systems. Raw footage and floor maps remain private; shared plots show derived estimates.
  3. Check initialization and output availability. Does it produce usable position estimates at all? Inspect missing periods before interpreting accuracy.
  4. Then inspect position error and drift. Compare only matching conditions, valid time support and stated scale/alignment policies.
  5. Check the map separately. A good position estimate does not prove a correct or complete map. Read native export status and known/unknown map cells.
  6. Inspect resources and repetitions. Memory/CPU show computational cost. Repeats show consistency on the same input, not performance in every environment.
Five common reading mistakes
  • “Green means good SLAM.” Green completed slots mean input/execution checks passed. A completed run can remain uninitialized.
  • “A blank error chart means zero error.” Blank usually means no eligible output or no valid score. It is unavailable, not perfect.
  • “The smallest error always wins.” A system working for one second can have low conditional error while failing for most of a thirty-minute input.
  • “More visited area means better mapping.” Reference path visitation is shared input context. Native confident map area is a different measurement and must be paired with accuracy.
  • “p95 means95% confidence.” p95 is a sample percentile:95% of the measured values lie at or below it. It is not a statistical confidence level.


Plain-language glossary and units
Ground truth / reference
The simulator's recorded robot position and orientation, used only by evaluation. It is the answer we compare estimates against; it is not sent into SLAM.
Pose / trajectory
A pose is position plus orientation at one time. A trajectory is the sequence of those poses.
Input time vs elapsed time
Input time is time within the saved simulation. Supervisor elapsed time is real running time of that replay. Recording can take longer than the simulated duration.
Initialization
The native system has established an initial estimate/map. Receiving images or staying alive does not establish initialization.
Eligible output / availability
An output that meets this entry's declared validity rule. DVM/COVINS require native OK and an associated pose. Custom exposes calibrated fused prediction; visual tracking validity is unknown.
Epoch / map ID / alignment
An epoch is one local coordinate period. A map ID labels a native reference map. After a reset/map change coordinates may differ. Alignment places the epoch's first pose onto the reference once; it does not repair later drift.
Monocular scale
One camera may reconstruct shape without knowing its physical size. DVM's plotted error uses a reference-fitted scale; that diagnostic does not prove the native robot knows metres correctly.
APE / XY error / RMSE
APE is position difference after the stated alignment. XY is horizontal position. RMSE combines errors with larger mistakes receiving more weight.0.05 m is5 cm. Error here is conditional on eligible samples.
RPE / drift
Relative pose error compares estimated motion over an interval with the reference motion over that interval. One-second RPE asks how wrong that small motion was. Small local drift can still accumulate into a poor global map.
Median / p95 / maximum
Median is the middle sample; p95 is the95th percentile; maximum is the worst recorded sample. Always inspect sample support and missing periods.
CDF
A cumulative distribution plot. At an x-axis error of0.1 m and a y-axis value0.9,90% of the eligible samples had error at most10 cm. This says nothing about frames with no valid pose.
CPU / RSS / MiB
CPU100% is one core's worth of work;400% is about four cores. RSS is sampled resident process memory.1 MiB is1,048,576 bytes. Container memory also includes helpers and cache.
Native confident map cells / unknown
Cells that pass the native map confidence threshold. Unknown cells have no confident classification; they are not counted as correct free space. Neutral values may also result from conflicting observations.
Precision / recall / IoU
Occupied precision asks how often a predicted obstacle agrees with reference. Conditional recall asks how many reference obstacles in the known-cell subset are found. IoU measures overlap. High conditional scores do not imply large map completeness.
Formal vs development data
Formal inputs were registered for the comparison. Development previews are earlier adapter checks, labelled and excluded from formal tables.
How the benchmark works: method, design and fairness
UNDERSTAND THE EXPERIMENT / WHAT · HOW · WHY
What is this benchmarking process?
Go to the measured results ↓


Benchmarking means testing systems under defined conditions and measuring their results. Our question is: How do DVM, COVINS and Custom SLAM perform on these recorded indoor mapping/localization inputs, using their declared sensor configurations? We examine whether they initialize, when they lose usable estimates, how their estimates differ from reference, what native map evidence exists, and the computing resources they use.

Exactly what is planned?
  • Nine five-minute recordings: ordinary, slow and turn-dominated motion at three fixed starting locations.
  • One thirty-minute recording: an endurance condition, run first to include a longer initialization and operating horizon.
  • Twelve seconds still at startup: a common input prerequisite for unchanged Custom calibration, supplied to all entries.
  • Ten recordings × three systems × three repetitions =90 native trial slots. Recording happens once per condition; replay is repeated.
  • Four CPUs per native trial, uncapped project RAM/swap. Data and original failures are preserved.
  • Minimum11¼ hours of native replay. Simulator capture, integrity checks, startup, shutdown and audit add real time. A thirty-minute recording is thirty minutes of simulated input, not a promise of thirty minutes on the clock.
These are three process repetitions of each saved input, not three new buildings. Formal outcomes remain separate from the labelled two-minute development previews.
Why record and replay instead of separate live runs?
Imagine giving three students the same exam paper. Here, the “paper” is a saved sensor recording. Each system sees the same scene sequence and motion, so a different route or a slightly different simulated encounter cannot quietly make its test easier.
It also lets us inspect a failure again from the preserved data and reuse that input for future SLAM entries. Changing an algorithm’s result must not change its input recording.
The tradeoff: the replayed SLAM does not drive the robot. This tests estimation and retained mapping output on shared motion. It does not test how each system would choose a route or react through a navigation controller.
Equal recordings do not mean equal information: the entries use different sensor channels and starting assumptions. We compare those declared deployments, not an isolated algorithm-only ranking.


Why these choices help, and what they still cannot guarantee
ChoiceWhy we do itRemaining limitation


Freeze the plan and preserve settingsReduces selecting only favourable conditions or tuning after seeing formal results.It does not establish that each native configuration is optimal for this environment.

What does each system receive?
DVM: the left camera, as its declared monocular deployment.
COVINS: paired stereo images and its native backend.
Custom: stereo images, wheel movement, gyro and a declared starting-dock prior. Continuing fused prediction does not prove its visual component is tracking.
Each uses the channels appropriate to this registered configuration. We do not invent extra sensor data or silently give all systems the same sensor capability.
What does “coverage” mean here?
Recorded-path visitation: where the reference robot body travelled. It is shared input context, so it cannot identify which SLAM mapped more.
Usable-pose support: how much of the camera input has estimates meeting that entry’s validity rule.
Native map completeness: how much space a mapper confidently and correctly represents. The current retained grid diagnostic is Custom-only; comparable DVM/COVINS map exports remain unqualified.
Do not substitute one of these meanings for another. Accurate localization alone does not certify a complete or geometrically correct map.


How do I recognize the current stage in the dashboard?
  • Recording: the capture time, saved image count and camera preview advance. Formal algorithm results may still be pending.
  • Replay: one native trial is active; its state, resource and timing logs begin to populate.
  • Evaluation: qualified completed-trial plots and tables appear after the stage passes its checks. Blank unsupported metrics stay unavailable.
  • Final audit: independent evidence checks remain pending until the planned study finishes. Check its explicit result; a fresh queue heartbeat is not an accuracy certificate.
  • Stale or failed: inspect the error and status age. The reporting-recovery amendment preserves the active recording; it does not change algorithm settings or make a failed scientific gate pass.


A conclusion we can defend: “On these predefined simulator recordings, these configurations showed the reported initialization, output support, local trajectory errors, retained map evidence and resource costs.” A universal best-SLAM claim, full-map accuracy claim or confidence percentage needs additional evidence beyond this study.


05 / REASON · CRITIQUE · CHANGE
What can we depend on?


Defensible conclusions
  • Which declared deployment initializes and produces usable output on each exact recorded condition.
  • Conditional local trajectory error, processing cost, resource use and repeat variability with their measurement boundaries.
  • Shared recorded robot motion and reference footprint visitation as input context.
Matched recorded inputs, frozen settings, evaluator-only ground truth and explicit failures follow established SLAM benchmarking principles. SLAMBench2 methodology ↗
Claims this study cannot support
  • A universal best SLAM, or an equal-sensor algorithm-only ranking.
  • Mapped/cleaned floor coverage, navigation decisions, collision avoidance or recovery success.
  • Real-world reliability, battery energy, collaboration, lighting or dynamic-scene robustness.
  • Statistical certainty from frames or three repeats on one recording. Scenes and repeated processes are different units.
Future closed-loop missions and additional independent real/simulated scenes are needed for those claims. No benchmark configuration is changed by this viewer.
